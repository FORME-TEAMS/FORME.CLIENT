# Падение при загрузке внешности, 26 ноября 2026

Новый macOS crash report от 26 ноября, 10:24:57 МСК: `EXC_BAD_ACCESS`, адрес
`0x7c`, главный поток, `LLAppearanceMgr::updateAppearanceFromCOF()` из отложенного
callback деструктора `LLUpdateAppearanceOnDestroy`. Это другой стек после исправления
панели групп. Отчёт получен на MacBookAir10,1 под Rosetta; он не содержит номера
строки C++ и не доказывает проблему Rosetta.

В соответствующем журнале клиент успешно устанавливает CAPS/UDP и доходит до
`STATE_INVENTORY_CALLBACKS`. В skeleton нет папок 48 и 50; виден успешный callback
создания только 48. До конца журнала нет перехода к следующему состоянию, а кешированный
`mCOFID` инициализировался только **после** ожидания системных папок. В это время
отложенные callbacks внешности уже могут вызывать `updateAppearanceFromCOF()`.

В исходниках подтверждены два дефекта:

- До проверки наличия COF выполнялись поиск ссылок, ограничения предметов и
  переупорядочивание одежды с `getCOF()`. Нулевой UUID нельзя использовать как
  корень этих операций: в выборку могут попасть посторонние предметы.
- В диагностике неполной COF результат `gInventory.getCategory()` разыменовывался
  без проверки. При отсутствующей категории это даёт обращение через null,
  согласующееся со стеком и низким адресом из crash report. Точную машинную
  инструкцию без символов этой macOS сборки не установили.

## Исправление

Сразу после загрузки skeleton клиент связывает менеджер внешности с существующей
COF, до ожидания создания остальных системных папок. `ensureCOF()` дополнительно
проверяет готовность инвентаря, тип категории, владельца и размещение под корнем
личного инвентаря. При пустом или устаревшем кеше повторно ищет уже загруженную
папку. Новую папку этот поиск не создаёт.

Проверка стоит перед любым обходом/исправлением COF в `updateAppearanceFromCOF()`.
Если категории ещё нет, операция прекращается без удаления предметов. Обычный
стартовый `callAfterCOFFetch(set_flags_and_update_appearance)` сохранён: он повторно
строит внешность после получения инвентаря. Бесконечных повторных HTTP-запросов нет.
Диагностика также проверяет указатель категории перед обращением к её версии.

В запасном пути без AIS добавлена такая же проверка перед `setFetching()`. При
отсутствии категории completion вызывается один раз; null не разыменовывается.
AIS-путь продолжает получать COF с сервера, даже если её ещё нет в локальном кеше.

## Проверка и ограничения

`python3 tests/forme/check_appearance_startup.py` компилирует и выполняет извлечённые
из production C++ функции разрешения COF, допуска обновления и диспетчеризации
загрузки. Граница инвентаря/сети заменена фикстурой. Включён UBSan с остановкой
при ошибке. Проверены пустой кеш, неготовый инвентарь, отсутствующая категория,
восстановление после её появления, устаревший UUID, другой владелец/тип/родитель,
обычный fetch, отсутствие категории при fetch и AIS fetch без локальной COF.
Отдельные проверки контролируют порядок startup и безопасность диагностики.
Отрицательный прогон с удалённым ранним `return` отвергается native-сценарием:
обновление недопустимо продолжилось после удаления категории. Рабочие исходники
при этом не подменялись.

Полный `python3 scripts/forme_preflight.py` включает этот набор. Это не компиляция
всего viewer: macOS линковка и повторный вход на реальном сервере ещё нужны.

HTTP 404 при попытках изменить библиотечные предметы и отсутствие обязательных
частей аватара в журнале зафиксированы. Ранний обход с пустой COF мог выбирать
посторонние предметы; после исправления это надо проверить повторным входом.
Причина отсутствующего callback папки 50 в данном журнале не установлена;
исправление нельзя считать доказательством устранения всех ошибок инвентаря.
Личные предметы, аккаунты и база данных не сбрасываются. Серверные INI не меняются.

Серверное отключение через 60 секунд без UDP-пакетов является следствием потери
клиентского процесса. Изменение этого таймаута не исправляет данный crash.

Для проверки новой сборки: войти тем же аккаунтом, дождаться завершения загрузки
внешности, проверить одежду/инвентарь и повторить вход. Сохранить новый журнал;
при повторном завершении — также свежий macOS crash report. Приёмка RWS-005
остаётся открытой.
